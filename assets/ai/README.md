### 設計図（外部データ方式）について
モデル丸ごと（例: unet 647MB）を onnxruntime-web に渡すと、wasm メモリへ複製されて約2.4倍に膨らみ、
iPhone（Safari のページ上限 約1.9GB）で強制終了していました。設計図＋元ファイルを `externalData` として渡すと、
重みは wasm を通らず GPU へ直接送られます。

| 計測（Chromium・WebGPU・fp32） | 旧方式 | 設計図方式 |
| --- | --- | --- |
| unet（1.23GB）作成後の wasm メモリ | 2967 MB | 16 MB |
| vae_decoder（0.19GB） | 412 MB | 16 MB |
| 出力 | — | 完全一致 |

設計図の重みは「元の model.onnx 内のバイト位置」を指すため、配布元のファイルを未改変のまま使えます。

モデル本体はリポジトリに含めず、利用者の端末が初回だけ Hugging Face から取得して OPFS に保存します。

| 種類 | 取得元（リビジョン固定 `fa62aea`） | 容量 | ライセンス |
| --- | --- | --- | --- |
| 標準（fp16） | `cursedhelm/aderpy-deepdreamer-onnx` の `tiny-sd-web-fp16` | 約 0.95 GB | CreativeML Open RAIL-M |
| 軽量（4bit） | 同 `tiny-sd-web-q4f16` | 約 0.60 GB | CreativeML Open RAIL-M |

元モデルは [`segmind/tiny-sd`](https://huggingface.co/segmind/tiny-sd)。CreativeML Open RAIL-M は個人利用を認める一方、
違法・有害な用途などを禁止しています。

検証:
- トークナイザ … Hugging Face `tokenizers` と 6/6 一致（日本語・記号・特殊トークン含む）
- スケジューラ … diffusers `DPMSolverMultistepScheduler` と誤差 3e-6 以内で一致（4〜40工程）
- ブラウザ（onnxruntime-web）と Node（onnxruntime-node）の出力 … 平均差 1/255

### iPhone の強制終了への対策（実機テスト第1〜8回の結論）
当時は iPhone の Safari に「JS のメモリ＋GPU のメモリ」の合計約1.9GBの上限があると推定していた（第9回で、主な原因は下記の3秒ルールと判明）。描画の作業メモリは
256×384 で約80MB・448×640 でも約625MB（グラフから計算）と小さく、問題は「モデルファイル（444〜647MB）を
丸ごとメモリへ読んだ写しが、GPU へ送った後も残ること」だった。

| 対策 | 内容 |
| --- | --- |
| Worker で実行 | 1枚ごとに Worker を作って捨てる → GPU を含むメモリが確実に返る |
| 重みを1個ずつ読む | OPFS の同期ハンドルで必要な分だけ読み、作業用の1枚を使い回す（最大56MB） |
| `.mjs` の修正（LGO3） | 外部データの読み出しを `readSlice` に対応／転送方式を切替可能に（既定は元の方式） |
| GPU バッファ | 使い回し（bucket）をやめ、使用後すぐ解放（lazyRelease） |
| GPU 接続の「つなぎ」 | onnxruntime-web 1.31 は最後のセッションを解放すると GPU 接続を破棄し、次の部品で作り直す。iPhone では文章部品→描画部品の切り替え直後の描画が毎回（通算10回）強制終了していたため、生成の間は極小モデル（x+x）のセッションを持ち続けて接続を保つ |
| 文章部品の要約出力を除去 | `pooler_output` はアプリで使わないが、ArgMax（最大値の位置）→その位置での読み出しという、データ次第の計算をしていた。`last_hidden_state` だけを残す（WebGPU 半精度で完全一致を確認） |
| 部品の URL に版 | Worker が読み込む部品だけ古い保存データが使われることがあったため、`?v=` を付ける（`local-gen.js` の `AV`、`index.html`、`diag-gen.html`、`sw.js` をそろえる） |

出力は修正前と完全一致（Chromium・WebGPU／CPU とも）。

### 大きい画像の作業メモリを減らす（実機テスト第8回の結論）
第8回で、描画部品だけを動かしても 192×256 以下は毎回成功・256×384 以上はほぼ毎回強制終了と分かった。
大きさで急に増えるのは次の2つで、どちらも「画素の並び」で小分けにしても計算結果は変わらない。

| 計算 | 448×640 での中間結果 | 小分け（`tools/slice_unet.py`） |
| --- | --- | --- |
| 自己注意（画素どうしの関係の表、画素数×画素数） | 1個 306MB | 問い合わせ側を最大解像度で32分割・1/2解像度で2分割 → 10MB 以下 |
| 全結合（1画素ずつ 320→2560→320 に拡大・縮小） | 1個 22MB | 入力を4分割（1/2解像度は2分割）→ 6MB 以下 |

| 計測（Dawn＋lavapipe・軽量モデル・GPU バッファの同時最大） | 192×256 | 256×384 | 448×640 |
| --- | --- | --- | --- |
| 元の設計図 | 501 MB | 596 MB | 1316 MB（出力が全部 NaN） |
| 小分け版 | — | 502 MB | 638 MB |

- 出力は元と完全一致（256×384・448×640 の軽量、128×128 の標準）。448×640 の元の版が NaN になるのは、表1個が
  「1回に結び付けられるバッファの上限」（Dawn は128MB。iPhone は1GB）を超えるため。Android 等でも起こりうる
- 1工程の GPU 命令数は 757 → 1303 に増える（lavapipe では所要時間ほぼ同じ）
- 分割数は `ATTN_CHUNKS` / `FF_CHUNKS`。分割位置は `Shape` から計算し、大きさが決まると onnxruntime が定数に畳み込む

### 強制終了の本当の原因: Safari の「3秒ルール」（実機テスト第9回の結論）
第9回で、GPU メモリは計算なしなら 1.5GB まで確保できた（メモリ量は原因ではない）。強制終了の記録
（解析データの `com.apple.WebKit.GPU-日付.ips`）は、`WebGPU::crashGPUProcess` ← `Queue::commitMTLCommandBuffer`
のタイマーだった。WebKit（`Source/WebGPU/WebGPU/Queue.mm`）は、GPU へ送った命令のまとまり（command buffer）が
**送ってから3秒以内に終わらないと GPU プロセスごと落とす**。onnxruntime は命令を一気に送るため、
大きい画像では後ろの命令が前の計算待ちで3秒を超えていた（448×640 は描画18工程を完走し、仕上げで落ちた）。

| 対策（`local-gen-run-worker.js` の `installPace`、`local-gen.js` の `pace`） | 内容 |
| --- | --- |
| 1回に送る命令を2個に | セッション設定 `ep.webgpuexecutionprovider.maxNumPendingDispatches`（既定16）。GPU 接続ごとに最初のセッションの値が効くので、つなぎ用セッションにも付ける |
| GPU に預ける量を抑える | 最近16回の実行時間の最大から、同時に預ける送信の数（2〜16）を決め、見積もり合計0.8秒以内にする。残りは手元の列で待たせ、終わった分だけ送る |
| 順序を保つ | 列が空でない間は `writeBuffer`（中身を写して）・バッファ破棄・`mapAsync`・`onSubmittedWorkDone` も同じ列に並べる |

Dawn＋lavapipe（軽量・128×128）で、送信の「待ち」の最大は 9.06秒 → 0.80秒、出力は完全一致、所要時間はほぼ同じ。

### 強制終了の確定した原因: ページのメモリ上限 2048MB（実機テスト第10〜11回の結論）
Mac のコンソールで iPhone のログを見ると、強制終了のたびに
`kernel memorystatus: com.apple.WebKit.WebContent exceeded mem limit: ActiveHard 2048 MB (fatal)` が出ていた。
WebKit は GPU バッファもページ側（WebContent）のメモリに数える（`Device::setOwnerWithIdentity`）。上の「3秒ルール」は、
ページ側が先に落ちた後、GPU 側の後片付け中に起きた二次的なものだった（クラッシュ記録が1件しか残らなかった理由）。

| 第11回の測定（軽量・256×384。32MB ずつ GPU バッファを確保し、落ちる直前の量＝余裕を記録） | 余裕 | 使用量 |
| --- | --- | --- |
| 何も読み込まない状態 | 1664 MB | — |
| 描画部品の読み込み直後 | 544 MB | 約1120 MB |
| 読み込み後、命令の完了＋3秒待ってから | 1280 MB | 約384 MB |
| 2回実行した後（送信の待ち合わせあり・3秒後） | 768 MB | 約896 MB |

- wasm のメモリは 19MB しか使わない（Dawn で計測）。使用量の大半は GPU 側
- 読み込み中に作られる GPU バッファは合計 1242MB（モデルは 443MB。転送用の一時バッファなど）。JS からは破棄済みでも、
  実際に返るまで時間差がある。返る前に描画を始めると上限を超える（「描画開始」直後に落ちていた理由）
- 対策（`local-gen.js` の `settle`、`local-gen-run-worker.js` の `settleGpu` / `gcPoke`）: 部品の読み込み後に、命令の完了を待ち、
  GC を促して、3秒待つ。描画の工程ごとにも GC を促す。送信の待ち合わせは既定で切った（`pace: { bypass: true }`。
  待たせた命令の殻が長生きして回収が遅れる疑いがあるため。第12回で比較する）

### 第12回の結果と、仕上げ（VAE）のタイル分割
読み込み後に待つ対策で、256×384 の描画18工程はページが落ちずに完走した。残った問題と対策:

| 問題（第12回） | 対策 |
| --- | --- |
| 送信の待ち合わせを切ると「GPU待ち」が3秒に達し、GPU 側が落ちる（仕上げ・448×640 の描画。`mapAsync` 失敗のエラーになる） | 待ち合わせを既定で入れ直した（`pace: { pending: 2, budget: 0.8, min: 2, max: 16 }`）。待ち合わせありの実機の「待ち」は最大1秒前後 |
| 仕上げは1回の実行で GPU バッファを大量に作る（Dawn 計測・軽量: 256×384 で合計 621MB → 448×640 なら約1.8GB） | 潜在表現が `vaeMaxArea`（1536 = 256×384 相当）を超えたらタイルに分けて順に復元し、重なり（潜在8画素 = 64px）をなだらかに混ぜる（`local-gen-core.js` の `planTiles` / `decodeTiled`）。448×640 は 2×2 |

実行後の使用量（256×384・上限 2048MB・基準 384MB）: 回収を促して0.3秒 576MB ／ 2回実行後 800〜1024MB ／ 6回実行・毎回回収 704MB（増え続けない）。

### GPU バッファは使い回す（実機テスト第13〜14回の結論）
診断ページでは 448×640 まで成功したが、アプリ本体では同じ軽量モデル・同じ条件でも描画の3〜4工程目で強制終了した
（余裕は診断ページ 1664MB・アプリ本体 1696MB で差なし）。当初アプリが落ちていたのは、両方保存されていると
標準モデル（描画部品 617MB）を選んでいたためで、iPhone / iPad は軽量を優先するようにした（`preferLight`）。

残る不安定さへの対策として、GPU バッファの方式を `lazyRelease`（毎回作って捨てる）から `simple`（同じ大きさを使い回す）に変えた。
実機の測定では、捨てたバッファが返るまでに秒単位の時間差があり、実行後の使用量が JS から見える量よりずっと多かった
（256×384 で 300〜600MB 多い）。使い回しなら churn が無く、時間差に左右されない。

| 計測（Dawn＋lavapipe・軽量・描画部品 256×384） | 1回目の実行 | 2回目以降 |
| --- | --- | --- |
| lazyRelease | 94 MB・1513個 作成 | 毎回 94 MB・1513個 作成 |
| simple（保存用・uniform とも） | 81 MB 作成（保持） | 約 0 MB・4個（128×128 で確認） |

出力は lazyRelease と完全一致。初期の実機テストで使い回し（bucket）をやめたのは、読み込み直後の一時メモリなど
別の原因が重なっていた時期の判断だった。

### 画質（第15回のあと）
アプリ本体で 448×640・25工程が完了するようになった（実機 143 秒）。次の2点で画質を上げた（どちらも index.html 側）。

| 症状 | 原因 | 対策 |
| --- | --- | --- |
| 肌・背景が油絵のようにのっぺり、縞が出る | 写真調は Real-ESRGAN general 4x で約4.8倍に拡大しており、細かい質感を塗りつぶす | `srFinish`: 元画像の滑らかな拡大を 45% 混ぜ、輝度だけの弱い粒子（標準偏差 3）を足す |
| 写実感が弱い | 指示文が CLIP の上限 75 語分を超え（実測 115）、末尾の「ピント・肌の質感」が毎回切り捨て | 端末内用に `localPrompt` / `localNegative` を作り、画質の指定を先頭に置く |

拡大の比較（PC・同じ元画像）: AI拡大のみ＝肌がのっぺり・目に不自然な模様、AIなし＝目の輪郭がギザギザ、混ぜる方式が最も自然。
ネットワーク経由の指示文は従来どおり（サーバー側のモデルは長い指示文を読める）。

### 全身の構図と「顔の描き直し」
全身（頭から足先まで）を 448×640 で描くと、顔は幅 50〜80px ほどしかなく、小型モデルでは崩れる（目が潰れる・幼く見える）。
上半身に寄せれば顔は整うが、全身が見えない。両立のため、全身を描いたあと顔だけを描き直す（`LocalGenCore.generate` の `opts.face`）。

| 手順 | 内容 |
| --- | --- |
| 1. 検出 | 仕上がった画像から顔を探す。YuNet（`models/yunet/`・232KB・MIT）を CPU(wasm) で実行。GPU のメモリは使わない |
| 2. 切り出し | 顔の枠を 2.2 倍に広げ、画像と同じ縦横比で切り出す（拡大率は最大4倍。1.5倍未満＝顔が十分大きい時は何もしない） |
| 3. 描き直し | 切り出した latent を全体サイズ（56×80）に拡大し、ノイズを載せて後半の工程だけやり直す（16工程中の後半8工程・顔のアップ用の指示文） |
| 4. 復元 | 仕上げ（VAE）で画像にする。描画・仕上げとも全体と同じ大きさなので、GPU の使い方は全体の生成と同じ |
| 5. 貼り付け | アプリ側（index.html `pasteFaceDetail`）が、拡大後の画像の同じ位置に楕円のぼかしマスクで貼る |

- 文章部品は最初に3件（禁止語・全体・顔）まとめて解析する。描画・仕上げの部品は読み直す（同時には持たない＝メモリ上限対策）。
- 失敗しても全体の画像はそのまま返す（顔が見つからない・顔検出モデルを読めない等）。
- 描き直し中に強制終了した場合は、次回から自動で OFF（⚙設定「🙂 顔の描き直し」で戻せる）。OFF や安全設定の時は上半身の構図にする。
- PC（CPU・軽量モデル）での確認: 全身構図の3枚とも顔を検出（幅 52〜82px）し、描き直し後は目が開いて顔立ちが整った。

#### 実機での最初の結果（版 2026-11-16a）と対策
開き直した直後の1回目は完走したが「ほぼ顔だけ・顔が歪む」、同じ画面での2回目は描画の1工程目で強制終了した（1回目の記録は上書きされて残らず）。

| 問題 | 推定（未確定） | 対策（版 2026-11-16b） |
| --- | --- | --- |
| ほぼ顔だけ・歪み | 顔が大きめの画像を広い範囲（最大で画像の2/3）で描き直し、顔のアップに寄って体とつながらなくなった | 2倍以上に拡大できる時だけ描き直す（`minZoom: 2`）。描き直した画像でもう一度顔を検出し、位置・大きさが元と合わなければ使わない |
| 2回目の強制終了 | 同じ画面での前の処理（生成・AI超解像）のメモリが返りきっていない | AI超解像のGPUバッファのプールを解放（`AI_SR.release`。実測は約25MBで主因とは言えない）。続けて生成する時は前の処理の終了から最大8秒待つ |

- 記録: 1つ前の生成記録も残す（`lg_local_log_prev`）。指示文の種類・この画面で何回目か・前の処理からの秒数を記録する。
- 続けての生成（2回目以降）で落ちた場合は安全設定に落とさない。アプリの版が変わったら安全設定を解く。

#### 版 2026-11-16b の実機結果と、タイル方式の検討（版 2026-11-16c）
開き直した直後の1回目でも描画の1工程目で強制終了した（「続けて生成したのが原因」という見立ては誤り）。
448×640 を1枚で描く方式は、使い回し方式にしてからも 成功4・失敗2（失敗はすべて描画の1工程目）で、上限ぎりぎり。256×384 は一度も落ちていない。

**タイル方式**（`opts.tile` / `opts.hires`）を実装した: 描画部品を常に 256×384 で動かし、①256×384 で構図 → ②448×640 に拡大して
後半の工程を重なりのあるタイル4枚でやり直す（ノイズ予測を重なり部分でなだらかに混ぜる）。メモリは 256×384 相当で済む。
ただし PC（CPU・軽量モデル）で確かめた画質が不十分で、**既定では使わない**（`tileOn: false`。`diag-gen.html?tile=1` で試せる）。

| 構図 | タイル方式の結果（PC） |
| --- | --- |
| 全身 | つなぎ目は見えず完走するが、構図を 256×384 で作ると人物が幼い体つきになりやすい。描き込みが強い（0.55）と体や服が別の物に化ける |
| 全身＋「大人・長身」を強調 | 頭が切れる・人物が消えるなど、構図が崩れる |
| ひざ上（cowboy shot） | 帽子が出る・顔が切れるなど、構図が安定しない |
| 上半身 | 顔が大写しになり、タイルごとに別の顔を描き込んで崩れる（目が増える等） |
| 顔の描き直しをタイルで | 顔が二重にぶれる → 顔は必ず1枚（描画部品の大きさ）で描くようにした |

同じ指示文でも、448×640 を1枚で描けば大人の体つきで全身が入る（前節）。つまり必要なのは「大きい画像を1枚で描いても落ちない」ことで、
どの大きさまでなら余裕があるかを実測する（診断 第16回: 描画部品を 256×384 / 320×480 / 384×576 / 448×640 で2回動かした直後の余裕）。

- 追加の対策: 描画部品を開いて最初の2回の推論のあとは、少し待ってメモリを返させる（落ちるのが毎回1工程目のため）。
- 前々回の「ほぼ顔だけ・歪み」は、その前に強制終了があって安全設定（256×384・上半身の指示文）で動いた可能性がある
  （256×384 では「上半身」の指示で顔の大写しになることを PC で確認）。

#### 半精度 WebGPU の再現環境（開発用）
Chromium 同梱の SwiftShader は半精度(f16)に非対応のため、Node.js ＋ Dawn（npm `webgpu`）＋ Mesa lavapipe
（`VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`）で、実際の軽量・標準モデルを WebGPU 半精度で通し生成できる。
ここでは通し生成がエラーなく完了し、計算プログラム55個・GPU メモリ最大540MB（128×128）だった。

### 第16回の測定と 17a の切り分け
診断（版 16c・iPhone 15 Pro）: 描画部品を2回動かした直後の余裕は 320×480: 896MB / 384×576: 736MB / 448×640: 608MB。
256×384 は 128MB だったが、直前の生成が強制終了した直後の測定で、端末側のメモリがまだ戻っていなかったとみられる（参考値）。

448×640 の生成は 15f〜ff32e99（顔の描き直しなし）で4回続けて成功し、16a〜16c（顔の描き直しあり）で3回続けて
描画の1工程目で強制終了した。描画部品だけなら 448×640 でも 608MB 残るので、描画の前の処理の違いを疑う。
描画の前で変わったのは文章部品の batch（2 → 3）だけなので、17a で batch 2 に戻し、顔用の指示文は同じセッションで
もう1回実行する形にした。診断ページは「顔あり → 顔なし → 顔あり」の3回の生成で比べる（測定は `?measure=1` の時だけ）。

### 第17回（17a）の結果と 17b の対策
診断（448×640・25工程）: 顔あり 💥（描画の1工程目）→ 顔なし ○ → 顔あり ○。顔の描き直しの有無は関係なかった。
落ちたのは毎回「開いた直後の最初の生成」で、落ちて読み込み直したあとは続けて成功している（16c の測定も同じ）。
開いた直後だけ GPU の計算部品（シェーダー）を一から作るため、その作成と大きな計算が重なって上限を超えるとみる（推定）。

| 対策（17b） | 内容 |
| --- | --- |
| 下準備 | 本番の前に描画部品を 128×192 で1回だけ動かし、シェーダーを小さいメモリで先に作る（`warmup`。出力は同一を確認） |
| 落ちた時 | 1回目の強制終了では軽い設定に落とさず、同じ設定でもう一度（2回続けて落ちたら従来どおり 256×384） |

17a の診断では、描画中に1回の GPU 待ちが約5分（278〜302秒）の所があった。画面が消えたかアプリが裏に回った時とみられる。

### 第18回（17b）の結果と 17c の対策
診断（448×640・25工程）: 顔あり ○（開いた直後でも成功・下準備の効果）→ 顔なし ○ → 顔あり 💥（顔の描き直しの最中）。
GPU バッファを使い回す方式（simple）では、使い終わった仕上げ部品（VAE）の作業用メモリも GPU 側に残る。
そのあと顔の描き直しで描画部品を 448×640 で動かすと、両方が重なって上限に近づく（推定）。
17c では仕上げのタイルを 32×44 → 24×32（`vaeMaxArea` 1536 → 768・9枚）にして、残る量を約半分にした
（PC で比較: 継ぎ目なし・平均差 4/255）。診断ページは顔の描き直しの段階（読込・実行・仕上げ）も記録する。

### 第19回（17c）の結果と 17d の対策
診断: 顔あり 💥（開いた直後・下準備の描画部品の読込中）→ 顔なし ○ → 顔あり ○（顔の描き直しまで完了・仕上げ9枚）。
落ちるのは毎回「アプリから診断ページを開いた直後の最初の生成」で、落ちたあと（＝新しいプロセス）は成功している。
アプリの画面は普通のリンクで移ると「戻る」用に裏で残り、同じメモリ枠（2048MB）を使い続ける。
ページの読み込み直しでは消えず、強制終了で初めて消えることと合う（推定）。
17d では診断ページへの移動・アプリへの戻りを `location.replace` にして、前の画面を残さない。診断には「戻る履歴」「来た経路」を記録する。
